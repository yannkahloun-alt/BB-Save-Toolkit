# Validated Target UI

**Status:** validated target / implementation reference

This directory is the stable repository-local handoff for the validated Battle
Brothers Save Toolkit Target UI. Its top-level target architecture is:

```text
Company | Level Up | Recruitment
```

Brother is a stable drill-down context within Company, not a fourth top-level
workspace. Company/Brother, Level Up, and Recruitment are each closed and
validated design surfaces.

## How to use these artifacts

- [`target_ui_spec.md`](target_ui_spec.md) is the final validated product and
  semantic specification. Its product and semantic contracts are normative
  unless the document explicitly marks a decision unresolved.
- [`target_ui_prototype.html`](target_ui_prototype.html) is the validated v16
  interactive UX prototype. Open it directly in a browser; it is a standalone
  HTML file with inline styles, scripts, and mock data and has no external or
  CDN dependencies. It is an interaction reference, not production code.
- [`implementation_roadmap.md`](implementation_roadmap.md) is the reconciled
  implementation sequence and dependency proposal.
- [`repo_reconciliation.md`](repo_reconciliation.md) maps the target design to
  the repository state and existing issue structure at handoff time.
- [`backlog_classification.md`](backlog_classification.md) records the source
  bundle's detailed backlog classification. Its suggested issue mutations were
  explicitly not applied by the source artifact and are not applied by this
  import.

Future implementation issues should link to these repository-local files rather
than copy the design contract or depend on chat, sandbox, or attachment access.
The roadmap and reconciliation documents capture a point-in-time plan; current
repository code and issue state remain authoritative for implementation status.

## Normative product contracts

The validated specification is normative for:

- the information architecture;
- the `Fact / Analysis / Intent / Recommendation` semantic boundaries;
- `AssignedBuild` versus `Best Fit` separation;
- Gear and Mechanics ownership;
- the `Scan → Decision → Explain` interaction model;
- the validated Company/Brother, Level Up, and Recruitment workflows;
- responsive and sticky/docked interaction contracts;
- Recruitment separation of Potential, Relevant Need, and Cost; and
- prior-only versus known-evidence semantics.

These contracts describe the intended product. They do not by themselves prove
that the current backend or public dataset can supply every represented state.

## Illustrative and mock content

The following are illustrative unless a separate production contract and
implementation establish them:

- brother and recruit names;
- prices and wages;
- percentages not generated by a production model;
- sample Run Health states; and
- future analytical capabilities without an implemented backend contract.

Do not infer backend capability from behavior or data demonstrated by the
prototype. In particular, mock interactions are not evidence that persistence,
identity, history, freshness, scenario analysis, or recruitment models already
exist.

## Repository boundary

These files are documentation and design references only. They must not be
imported by production code, packaged as a production UI, or used as runtime
data. Implementations must not:

- turn the prototype into production code;
- change analysis semantics merely to match mock behavior;
- modify the current report renderer merely to resemble the target UI;
- treat mock values as backend truth; or
- hide unresolved backend or public-dataset requirements behind prototype
  behavior.
